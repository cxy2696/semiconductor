# 运营模式：谁在维护、多久一次、坏了怎么办

版本 2.0 · 2026-11-11

本文件定义 SiliconScope 的日常运营：角色、节奏、SLO、监控、故障处理、变更管理与成本。目标是**一个人也能长期维护，两个人也不会互相踩脚**。

## 1. 运营原则

1. **自动化优先**：能由 CI 完成的，不写进人的待办。
2. **失败可见**：宁可页面显示“数据过期”，也不静默使用旧数据。
3. **小步变更**：数据、内容、方法分开提交，便于回滚。
4. **可核查**：任何结论都能追溯到快照、字段定义与提交记录。
5. **低边际成本**：无服务器、无数据库、无付费 API；新增一家公司只改一行。

## 2. 角色与职责

| 角色 | 职责 | 当前承担 |
| --- | --- | --- |
| Maintainer | 合并 PR、发版、处理 CI 失败、维护方法 | 仓库所有者 |
| Data steward | 主数据、分类、符号映射、数据异常复核 | Maintainer 兼 |
| Content editor | 知识长文、术语、方法页文案 | Maintainer 兼 |
| Translator / reviewer | 英 / 日版本的一致性与术语审校 | 社区贡献 |
| Consumer | 使用站点，提交数据纠正 | 公开 |

角色可以兼任，但**方法变更**必须由 Maintainer 审核；**三语内容**至少经过一次非机器校对。

## 3. 节奏

| 频率 | 动作 | 负责人 | 产出 |
| --- | --- | --- | --- |
| 每个交易日 08:30（UTC+8） | CI 自动 `fetch + build + validate + deploy` | 自动化 | 新快照、站点 |
| 每周一 | 检查覆盖率、错误列表、过期标记 | Data steward | 异常清单 |
| 每月第一个工作日 | 复核 124 家样本与分类；检查失效官网与退市 | Data steward | universe 变更 PR |
| 每季度 | 复核方法、局限、SLO；更新路线图 | Maintainer | 方法版本 / CHANGELOG |
| 每半年 | 审校三语内容与术语一致性 | Content / Translator | 内容 PR |
| 按需 | 数据纠错、来源变更、政策事件 | 任何人 | Issue / PR |

> 非交易日不强制刷新；CI 仍会运行，但数据日期不变，页面显示 `as_of`。

## 4. 服务目标（SLO）

| 指标 | 目标 | 度量 | 未达标处理 |
| --- | --- | --- | --- |
| 构建成功率 | ≥ 99% / 月 | Actions 运行结果 | 按 §6 处理 |
| 数据新鲜度 | 交易日 `as_of` ≤ 24h，占比 ≥ 95% | 快照 `as_of` | 检查上游 |
| 行情覆盖率 | ≥ 90% | `coverage.ratio` | 检查符号映射 |
| 页面可用性 | ≥ 99.9% / 月 | GitHub Pages 状态 | 等待平台恢复 |
| 构建时长 | ≤ 10 分钟 | Actions 日志 | 减少请求 / 并发 |
| 单页体积 | HTML ≤ 200KB，CSS+JS ≤ 80KB | 构建检查 | 优化模板 |
| 测试通过 | 100% | CI | 阻断合并 |
| 三语对齐 | 100% | `validate_data()` | 阻断合并 |

## 5. 监控信号

没有独立监控系统，使用**可观察的产物**：

1. **GitHub Actions**：每日运行是否成功、耗时、失败步骤。
2. **`data/snapshots/latest.json`**：`coverage`、`errors`、`dataset`、`generated_at`。
3. **页面**：首页过期提示、页脚数据时点、关于页的错误列表。
4. **`semcore validate`**：数据契约与产物完整性。
5. **GitHub Issues**：读者反馈的数据错误。

建议每季度导出一次 `coverage` 与 `errors` 做趋势对比。

## 6. 故障处理（Runbook）

### 6.1 行情源整体不可用

**症状**：`fetch` 大量错误，`coverage` 骤降，页面显示旧数据。

1. 查看 `data/snapshots/latest.json` 的 `errors` 与 `coverage`。
2. 用 curl 直接请求一个已知标的，确认是网络/上游问题：
   ```bash
   curl -s "https://push2.eastmoney.com/api/qt/stock/get?secid=1.688981&fltt=2&fields=f43,f57,f58"
   ```
3. 若上游故障：**不要**手动改数据。保留旧快照，让 CI 以 `stale` 状态部署，并在 Issue 记录。
4. 若接口字段变化：更新 `QUOTE_FIELDS` 与解析，补测试，发补丁版本。
5. 恢复后手动触发一次 `workflow_dispatch`，确认覆盖率回到 ≥ 90%。

### 6.2 单只标的解析失败

**症状**：`errors` 出现 `<id>: symbol not resolved`，关于页列出。

1. 检查 `data/symbols.json` 是否有该 id 的 `secid`。
2. 用东方财富搜索接口确认代码与市场号：
   ```bash
   curl "https://searchapi.eastmoney.com/api/suggest/get?input=NVDA&type=14&token=D43BF722C8E33BDC906FB84D85E326E8&count=5"
   ```
3. 在 `symbols.json` 手工写入 `secid`，注明 `method: "seed"` 与 `checked` 日期。
4. 重新 fetch，核对名称、价格、币种与市值量级。
5. 若确实无可靠来源：设 `quote_venue = "unpriced"`，页面会显示说明并排除统计。

### 6.3 汇率失败

**症状**：`fx.status = stale/fallback`，跨币种市值偏差。

1. 检查 `open.er-api.com` 是否可达。
2. 系统会自动回退东方财富外汇对，再回退上一份快照。
3. 若长期失败：更新 `sources/fx.py` 的 `STATIC_FALLBACK`（记录日期），并在 Issue 说明。
4. 不得手工写入未经核实的汇率。

### 6.4 新闻抓取失败

**症状**：首页“行业动态”为空或使用旧数据。

- 新闻是**非关键路径**：构建不应因此失败。
- 检查 feed URL 是否变更；更新 `config.RSS_FEEDS`。
- 若某媒体长期不可用，从白名单移除并记录。

### 6.5 构建失败

1. 看 Actions 日志定位步骤：`refresh` / `validate` / `deploy`。
2. 本地复现：
   ```bash
   python -m semcore build
   python -m semcore validate
   python -m pytest
   ```
3. 若是数据问题：修复 `universe.csv` / `taxonomy.json` / 内容 front matter。
4. 若是模板问题：本地 `serve` 检查页面，补构建测试。
5. 回滚：`git revert` 最近提交，重新触发部署。

### 6.6 页面结构或样式错误

1. 明确影响范围（单页 / 单语言 / 全站）。
2. 本地构建并截图对比。
3. 修复后运行全量测试与 `validate`。
4. 若是第三方字体/浏览器兼容问题：优先使用系统字体栈，不引入 CDN。

### 6.7 数据错误（读者反馈）

1. 要求提供来源（公告、交易所页面）。
2. 判断是**源错误**还是**映射错误**：
   - 源错误：在 Issue 记录，等待上游修正，不做手工覆盖。
   - 映射错误：修 `symbols.json` 或 `universe.csv`。
3. 修复后在 `CHANGELOG.md` 记录，并在 Issue 回复。

### 6.8 安全事件

- 仓库无密钥、无数据库、无用户数据；主要风险是依赖漏洞与恶意 PR。
- 启用 Dependabot；审阅外部 PR 的 workflow 变更。
- 不在 Actions 中使用 `pull_request_target` 执行不可信代码。
- 若发现恶意内容：立即回滚、轮换 GitHub Token、审查最近部署。

## 7. 变更管理

### 7.1 提交类型

| 类型 | 影响 | 要求 |
| --- | --- | --- |
| 数据修正 | 单家公司 / 单个术语 | 附来源，更新快照或主数据 |
| 内容新增 | 知识长文 / 术语 | 三语齐全，CI 通过 |
| 样式 / 模板 | 全站视觉 | 截图对比，检查移动端与深色模式 |
| 方法变更 | 分数、清单、状态 | 更新 METHODOLOGY + 站内页 + CHANGELOG + 主版本号 |
| 依赖升级 | 构建环境 | 锁定版本，跑全量测试 |

### 7.2 版本号

- **主版本**：信息架构、评分方法、数据契约不兼容变更。
- **次版本**：新增页面、语言、数据源、覆盖扩展。
- **补丁**：数据修正、文案、样式修复。

### 7.3 发布流程

1. PR → CI（`quality.yml`：测试 + 数据校验 + 构建）。
2. 审核：数据变更看来源，方法变更看影响，内容变更看三语。
3. 合并到 `main` → `pages.yml` 构建并部署。
4. 更新 `CHANGELOG.md` 与版本号（如适用）。
5. 部署后抽查：首页、公司页、一个知识页、一个语言版本。

## 8. 治理

### 8.1 样本准入

新增公司需满足：

- 上市且可交易；
- 半导体收入为主（或明确标注为相关环节）；
- 有可靠行情源；
- 填补环节 / 地区空缺，或为关键龙头。

移除条件：退市、被并购、业务转型、连续 6 个月无可靠数据。

### 8.2 分类争议

- 以最近一个财年主要收入来源为准；
- 争议在 PR 中列证据（年报分部收入）；
- 无法判定时保留在“模组/系统”或“设计”，并在公司备注说明。

### 8.3 方法治理

- 任何权重调整需提供离线对比（分数分布、清单变化）。
- 阈值调整需说明动机与影响。
- 不接受“为了让某家公司入选”而调整方法。

### 8.4 内容治理

- 原创解释，附参考来源；不复制受版权保护的全文。
- 三语版本信息量对等，不做“英文精简版”。
- 每篇文章标注更新日期与难度。

## 9. 成本

| 项目 | 用量 | 成本 |
| --- | --- | --- |
| GitHub Actions | 每日 1 次 × ~5 分钟 + PR | 公开仓库免费额度内 |
| GitHub Pages | 静态托管 | 免费 |
| 行情 / 汇率 / RSS | 公开接口 | 免费 |
| 域名 | 默认 `github.io` | 0；自定义域名另计 |

**目标：月度现金成本 0；维护者时间 ≤ 2 小时/月（不含内容创作）。**

## 10. 备份与回滚

- 代码与快照在 Git 历史中，天然备份。
- 站点可从任意提交重建：`git checkout <sha> && python -m semcore build`。
- 部署回滚：Revert 提交并重新运行 `pages.yml`。
- 快照保留最近 30 份；更早的数据可从 Git 历史恢复。

## 11. 依赖与许可

- 运行时依赖仅 `jinja2`、`requests`；测试依赖 `pytest`。
- 依赖升级走 PR，锁定主版本范围。
- 数据与新闻版权归提供方；本站不转售、不批量再分发。
- 本站代码 MIT，文字 CC BY 4.0。

## 12. 退役预案

若项目停止维护：

1. 在 README 与首页标注“已停止更新”与最后数据日期。
2. 保留仓库与 `docs/` 只读，不删除历史。
3. 导出 `data/snapshots/latest.json` 与 `latest_data.json`，说明字段口径。
4. 移除 Actions 定时任务，避免继续请求上游。
