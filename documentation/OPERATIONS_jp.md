# 運用：誰が、どのくらいの頻度で保守し、壊れたときにどうするか

バージョン 3.0 · 2026-11-11

本ドキュメントは SiliconScope の日々の運用を定義します。役割、ケイデンス、SLO、監視、インシデント対応、変更管理、コストです。目標は、**1 人で無期限に保守でき、2 人が互いの邪魔をしない**ことです。

## 1. 運用原則

1. **まず自動化**：CI にできることは、人間の ToDo リストに入れません。
2. **失敗を見える化する**：古いデータを黙って使うより、「データが古い」と表示するほうがましです。
3. **小さく変える**：データ、コンテンツ、手法は別々にコミットし、それぞれを巻き戻せるようにします。
4. **検証可能**：すべての結論は、スナップショット、フィールド定義、コミットまでたどれます。
5. **限界費用が低い**：サーバーなし、データベースなし、有料 API なし。企業を 1 社追加するのは 1 行の変更です。

## 2. 役割と責務

| 役割 | 責務 | 現在の担当 |
| --- | --- | --- |
| メンテナー | プルリクエストのマージ、リリース、CI 失敗への対応、手法のオーナー | リポジトリの所有者 |
| データスチュワード | マスタデータ、分類、シンボルマッピング、データ異常のレビュー | メンテナーが兼務 |
| コンテンツエディター | 12 本の長編トピック、用語集、手法ページの文言 | メンテナーが兼務 |
| 翻訳者 / レビュアー | 中国語・日本語・ドイツ語の一貫性と用語のレビュー | コミュニティのコントリビューター |
| 利用者 | サイトを利用し、データの訂正を提出 | 一般公開 |

役割は兼務できますが、**手法の変更**はメンテナーのレビューを必須とし、**英語以外の各版**は少なくとも 1 回、機械翻訳以外のレビューを受ける必要があります。英語が正典であり、翻訳は要約版ではなく同じ情報を持たなければなりません。

## 3. ケイデンス

| 頻度 | 作業 | 担当 | 成果物 |
| --- | --- | --- | --- |
| 取引日ごとの 08:30 UTC+8 | CI が `fetch + build + validate + deploy` を自動実行 | 自動化 | 新しいスナップショット、サイト |
| 毎週月曜 | カバレッジ、エラー一覧、stale フラグを確認 | データスチュワード | 異常リスト |
| 毎月第 1 営業日 | 175 社のサンプルと分類を見直し、リンク切れの Web サイトと上場廃止を確認 | データスチュワード | ユニバース変更のプルリクエスト |
| 四半期ごと | 手法、限界、SLO を見直し、ロードマップを更新 | メンテナー | 手法バージョン / 変更履歴 |
| 半年ごと | 4 言語すべての 12 トピックと用語集の用語の一貫性を監査 | コンテンツエディター / 翻訳者 | コンテンツのプルリクエスト |
| 随時 | データ訂正、ソース変更、政策イベント | 誰でも | Issue / プルリクエスト |

> 非取引日は更新を必須としません。CI は実行されますがデータの日付は変わらず、ページには `as_of` が表示されます。

## 4. サービスレベル目標（SLO）

| 指標 | 目標 | 測定方法 | 未達時の対応 |
| --- | --- | --- | --- |
| ビルド成功率 | 月次 99% 以上 | Actions の実行結果 | §6 に従う |
| データ鮮度 | 取引日の `as_of` が 24 時間以内、95% 以上の確率で | スナップショットの `as_of` | 上流を確認 |
| 株価カバー率 | 90% 以上 | `coverage.ratio` | シンボルマッピングを確認 |
| ページ可用性 | 月次 99.9% 以上 | GitHub Pages のステータス | プラットフォームの復旧を待つ |
| ビルド時間 | 10 分以内 | Actions のログ | リクエスト数 / 並列度を調整 |
| ページ重量 | HTML ≤ 400 KB（最大のページは企業インデックス）、CSS + JS ≤ 80 KB | ビルド時のチェック | テンプレートを最適化 |
| テストの合格 | 100% | CI | マージをブロック |
| 4 言語の整合 | 100% | `validate_data()` | マージをブロック |

## 5. 監視シグナル

専用の監視システムはなく、**観測可能な成果物**を使って監視します。

1. **GitHub Actions**：日次実行の成否、所要時間、失敗したステップ。
2. **`data/snapshots/latest.json`**：`coverage`、`errors`、`dataset`、`generated_at`。
3. **ページ**：ホームページの stale 通知、フッターのデータ時点、「このサイトについて」ページのエラー一覧。
4. **`semcore validate`**：データ契約と成果物の完全性。
5. **GitHub Issues**：読者から報告されたデータの誤り。

四半期に一度、`coverage` と `errors` をエクスポートして傾向を比較します。

### 5.1 サイト上の状態とガイド

`/status.html` はヘルスチェックの画面版です。ビルド時刻とスナップショット時刻、データ経過時間、充足度、価格なしの銘柄、出典、ニュース件数、最近のスナップショット、古いコンテンツを表示します。`python -m semcore status` は同じ要約を Markdown で出力し、Pages ワークフローが実行サマリーに追記します。

`/guide.html` は3つの読書パス、色と充足度の約束、サイトマップ、キーボードショートカットを説明します。ページやデータ項目を追加したら、ガイドも更新して案内を正確に保ちます。


## 6. インシデント対応ランブック

### 6.1 株価ソースがまったく利用できない

**症状**：`fetch` のエラーが多発し、`coverage` が急落し、ページのデータが古くなる。

1. `data/snapshots/latest.json` の `errors` と `coverage` を確認します。
2. 既知の銘柄を curl で直接リクエストし、ネットワークか上流の問題かを切り分けます：
   ```bash
   curl -s "https://push2.eastmoney.com/api/qt/stock/get?secid=1.688981&fltt=2&fields=f43,f57,f58"
   ```
3. 上流が落ちている場合：データを**手作業で編集しないでください**。前回のスナップショットを保持し、CI に `stale` 状態のままデプロイさせ、インシデントを Issue に記録します。
4. インターフェースのフィールドが変わった場合：`QUOTE_FIELDS` とパーサーを更新し、テストを追加してパッチリリースを出します。
5. 復旧後、`workflow_dispatch` を手動で実行し、カバレッジが 90% 以上に戻ったことを確認します。

### 6.2 特定の銘柄が解決できない

**症状**：`<id>: symbol not resolved` が `errors` と「このサイトについて」ページに表示される。

1. `data/symbols.json` にその ID の `secid` があるか確認します。
2. Eastmoney の検索エンドポイントでコードと市場番号を確認します：
   ```bash
   curl "https://searchapi.eastmoney.com/api/suggest/get?input=NVDA&type=14&token=D43BF722C8E33BDC906FB84D85E326E8&count=5"
   ```
3. `secid` を手作業で `symbols.json` に書き込み、`method: "seed"` と `checked` の日付を記録します。
4. 再取得して、名称、株価、通貨、時価総額の桁を確認します。
5. 信頼できるソースが本当にない場合は `quote_venue = "unpriced"` を設定します。ページにその旨が表示され、その企業は統計から除外されます。

### 6.3 為替の失敗

**症状**：`fx.status = stale/fallback`、通貨をまたぐ時価総額がおかしい。

1. `open.er-api.com` に到達できるか確認します。
2. システムは自動で Eastmoney の通貨ペア、次に前回のスナップショットへフォールバックします。
3. 障害が続く場合は `sources/fx.py` の `STATIC_FALLBACK` を更新し（日付を記録）、Issue で説明します。
4. 検証していないレートを手作業で書き込まないでください。

### 6.4 ニュース取得の失敗

**症状**：ホームページの「産業ニュース」セクションが空、または古い。

- ニュースは**非クリティカルパス**です。これを理由にビルドを失敗させてはいけません。
- フィード URL が変わっていないか確認し、`config.RSS_FEEDS` を更新します。
- ある媒体が長期間利用できない場合は、ホワイトリストから外して理由を記録します。

### 6.5 ビルドの失敗

1. Actions のログを読み、`refresh` / `validate` / `deploy` のどのステップかを特定します。
2. ローカルで再現します：
   ```bash
   python -m semcore build
   python -m semcore validate
   python -m pytest
   ```
3. データの問題なら `universe.csv`、`taxonomy.json`、コンテンツのフロントマターを修正します。
4. テンプレートの問題なら `serve` をローカルで実行してページを確認し、ビルドテストを追加します。
5. 直前のコミットを `git revert` してロールバックし、再度デプロイをトリガーします。

### 6.6 ページ構造やスタイルのリグレッション

1. 範囲を特定します：1 ページ / 1 言語 / サイト全体。
2. ローカルでビルドし、スクリーンショットを比較します。
3. 修正後、全テストスイートと `validate` を実行します。
4. サードパーティのフォントやブラウザ互換性の問題なら、システムフォントスタックを優先し、CDN は追加しません。

### 6.7 読者から報告されたデータの誤り

1. 出典（開示資料や取引所のページ）を確認します。
2. **ソースの誤り**か**マッピングの誤り**かを判別します。
   - ソースの誤り：Issue に記録し、上流の訂正を待ちます。手作業で上書きしません。
   - マッピングの誤り：`symbols.json` または `universe.csv` を修正します。
3. 修正内容を `CHANGELOG.md` に記録し、Issue に返信します。

### 6.8 セキュリティインシデント

- リポジトリにはシークレットもデータベースもユーザーデータもありません。主なリスクは依存関係の脆弱性と悪意あるプルリクエストです。
- Dependabot を有効にし、外部からのプルリクエストではワークフローの変更をレビューします。
- Actions で `pull_request_target` を使って信頼できないコードを実行しないでください。
- 悪意あるコンテンツを見つけた場合：直ちに巻き戻し、GitHub トークンをローテーションし、最近のデプロイを監査します。

## 7. 変更管理

### 7.1 変更の種類

| 種類 | 影響範囲 | 要件 |
| --- | --- | --- |
| データ訂正 | 1 社 / 1 用語 | 出典を添付し、スナップショットまたはマスタデータを更新 |
| コンテンツ追加 | 長編トピック / 用語集 | 4 言語すべてで完成させ、CI を通す |
| スタイル / テンプレート | サイト全体の見た目 | スクリーンショット比較。モバイルとダークモードを確認 |
| 手法の変更 | スコア、スクリーン、市場状態 | METHODOLOGY + サイトページ + CHANGELOG + メジャーバージョンを更新 |
| 依存関係の更新 | ビルド環境 | バージョンを固定し、全テストスイートを実行 |

### 7.2 バージョン番号

- **メジャー**：後方互換性のない情報アーキテクチャ、スコアリング手法、データ契約の変更。
- **マイナー**：新しいページ、言語、データソース、カバレッジの拡大。
- **パッチ**：データ訂正、文言やスタイルの修正。

### 7.3 リリースフロー

1. プルリクエスト → CI（`quality.yml`：テスト + データ検証 + ビルド）。
2. レビュー：データ変更は出典、手法変更は影響範囲の記載、コンテンツ変更は 4 言語すべてが必要です。
3. `main` にマージ → `pages.yml` がビルドとデプロイを実行。
4. 必要に応じて `CHANGELOG.md` とバージョン番号を更新。
5. デプロイ後、ホームページ、企業ページ、ナレッジページ、各言語版の 1 ページをスポットチェックします。

## 8. ガバナンス

### 8.1 サンプルの受け入れ

新しい企業は次を満たす必要があります。

- 上場して取引可能であること。
- 売上の大半が半導体であること（または隣接する工程として明示的にラベル付けされること）。
- 信頼できる株価ソースがあること。
- 工程や地域の空白を埋める、または主要なリーダーであること。

除外の基準：上場廃止、買収、事業転換、6 か月連続で信頼できるデータがないこと。

### 8.2 分類の争い

- 直近年度の主な収益源を使います。
- プルリクエストで根拠（年次報告書のセグメント売上）を示します。
- 本当に曖昧な場合は、その企業を「モジュール / システム」または「設計」に残し、企業メモで説明します。

### 8.3 手法のガバナンス

- ウエイトの調整にはオフライン比較（スコア分布、スクリーンの変化）が必要です。
- 閾値の調整には、動機と影響の明示が必要です。
- 特定の企業をスクリーンに出すためだけに手法を変えてはいけません。

### 8.4 コンテンツのガバナンス

- 参考文献を明示した独自の解説とし、著作権で保護された文章を全文転載しません。
- 4 言語すべてが同等の情報を持ちます。「英語の完全版」と短縮訳を作らないでください。
- すべての記事は更新日と難易度を記録します。

## 10. バックアップとロールバック

- コードとスナップショットは Git の履歴にあり、それが自然なバックアップになります。
- サイトは任意のコミットから再ビルドできます：`git checkout <sha> && python -m semcore build`。
- デプロイのロールバック：コミットを revert し、`pages.yml` を再実行します。
- 直近 30 件のスナップショットを保持し、それより古いデータは Git の履歴から復元できます。

## 11. 依存関係とライセンス

- 実行時の依存関係は `jinja2` と `requests` のみで、テストには `pytest` を使います。
- 依存関係の更新はプルリクエストを経て、メジャーバージョンの範囲を固定します。
- データとニュースの著作権は提供元に帰属し、本サイトは再販や一括再配布を行いません。
- コードは MIT、文章は CC BY 4.0 です。

## 12. 終了計画

プロジェクトの保守が止まった場合：

1. README とホームページに「更新終了」と表示し、最終データ日を明記します。
2. リポジトリと `docs/` は読み取り専用で残し、履歴は削除しません。
3. `data/snapshots/latest.json` と `latest_data.json` を、フィールド定義の説明とともにエクスポートします。
4. 上流へのリクエストを止めるため、スケジュールされた Actions ワークフローを削除します。
