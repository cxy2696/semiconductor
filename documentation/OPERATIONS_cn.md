# 运营模式：谁在维护、多久一次、坏了怎么办

版本 3.0 · 2026-11-11

本文件定义 SiliconScope 的日常运营：角色、节奏、SLO、监控、故障处理、变更管理与成本。目标是**一个人也能长期维护，两个人也不会互相踩脚**。

## 1. 运营原则

1. **自动化优先**：能由 CI 完成的，不写进人的待办。
2. **失败可见**：宁可页面显示“数据过期”，也不静默使用旧数据。
3. **小步变更**：数据、内容与方法分开提交，便于分别回滚。
4. **可核查**：任何结论都能追溯到快照、字段定义与提交记录。
5. **低边际成本**：无服务器、无数据库、无付费 API；新增一家公司只改一行。

## 2. 角色与职责

| 角色 | 职责 | 当前承担 |
| --- | --- | --- |
| Maintainer | 合并 PR、发版、处理 CI 失败、维护方法 | 仓库所有者 |
| Data steward | 主数据、分类、符号映射、数据异常复核 | Maintainer 兼 |
| Content editor | 12 篇知识长文、术语表、方法页文案 | Maintainer 兼 |
| Translator / reviewer | 中文、日文与德文版本的一致性与术语审校 | 社区贡献者 |
| Consumer | 使用站点，提交数据纠正 | 公开 |

角色可以兼任，但**方法变更**必须由 Maintainer 审核，**每个非英文版本**至少经过一次非机器审校。英文是权威来源；译本必须承载同样的信息，而不是缩短版。

## 3. 节奏

| 频率 | 动作 | 负责人 | 产出 |
| --- | --- | --- | --- |
| 每个交易日 08:30（UTC+8） | CI 自动运行 `fetch + build + validate + deploy` | 自动化 | 新快照、站点 |
| 每周一 | 检查覆盖率、错误列表与过期标记 | Data steward | 异常清单 |
| 每月第一个工作日 | 复核 175 家公司样本与分类；检查失效官网与退市 | Data steward | universe 变更 PR |
| 每季度 | 复核方法、局限与 SLO；更新路线图 | Maintainer | 方法版本 / 变更日志 |
| 每半年 | 审校四种语言的 12 个主题与术语表，检查术语一致性 | Content editor / translators | 内容 PR |
| 按需 | 数据纠错、来源变更、政策事件 | 任何人 | Issue / PR |

> 非交易日不强制刷新；CI 仍会运行，但数据日期不变，页面显示 `as_of`。

## 4. 服务目标（SLO）

| 指标 | 目标 | 度量 | 未达标处理 |
| --- | --- | --- | --- |
| 构建成功率 | 每月 ≥ 99% | Actions 运行结果 | 按 §6 处理 |
| 数据新鲜度 | 交易日 `as_of` ≤ 24h，占比 ≥ 95% | 快照 `as_of` | 检查上游 |
| 行情覆盖率 | ≥ 90% | `coverage.ratio` | 检查符号映射 |
| 页面可用性 | 每月 ≥ 99.9% | GitHub Pages 状态 | 等待平台恢复 |
| 构建时长 | ≤ 10 分钟 | Actions 日志 | 减少请求 / 并发 |
| 页面体积 | HTML ≤ 400 KB（公司索引是最大页面）；CSS + JS ≤ 80 KB | 构建检查 | 优化模板 |
| 测试通过 | 100% | CI | 阻断合并 |
| 四语对齐 | 100% | `validate_data()` | 阻断合并 |

## 5. 监控信号

没有独立的监控系统；项目使用**可观察的产物**：

1. **GitHub Actions**：每日运行是否成功、耗时与失败步骤。
2. **`data/snapshots/latest.json`**：`coverage`、`errors`、`dataset` 与 `generated_at`。
3. **页面**：首页的过期提示、页脚的数据时点、关于页的错误列表。
4. **`semcore validate`**：数据契约与产物完整性。
5. **GitHub Issues**：读者反馈的数据错误。

每季度导出一次 `coverage` 与 `errors`，用于对比趋势。

### 5.1 站内状态与浏览指南

`/status.html` 是健康检查的页面版本：构建与快照时间、数据年龄、覆盖率、未定价标的、来源、资讯数量、最近快照与过期内容。`python -m semcore status` 输出同一份 Markdown 摘要，Pages 工作流会把它追加到运行摘要中。

`/guide.html` 说明六个实用任务、哪个页面回答哪个问题、颜色与完整度约定、常见问题与快捷键。新增页面或数据字段时，请同步更新指南，保证导航始终准确。


## 6. 故障处理（Runbook）

### 6.1 行情源整体不可用

**症状**：`fetch` 出现大量错误，`coverage` 骤降，页面显示旧数据。

1. 查看 `data/snapshots/latest.json` 的 `errors` 与 `coverage`。
2. 用 curl 直接请求一个已知标的，确认是网络还是上游问题：
   ```bash
   curl -s "https://push2.eastmoney.com/api/qt/stock/get?secid=1.688981&fltt=2&fields=f43,f57,f58"
   ```
3. 若上游故障：**不要**手工改数据。保留上一份快照，让 CI 以 `stale` 状态部署，并在 Issue 中记录。
4. 若接口字段发生变化：更新 `QUOTE_FIELDS` 与解析逻辑，补充测试，并发布补丁版本。
5. 恢复后手动触发 `workflow_dispatch`，确认覆盖率回到 ≥ 90%。

### 6.2 单只标的解析失败

**症状**：`errors` 与关于页出现 `<id>: symbol not resolved`。

1. 检查 `data/symbols.json` 是否包含该 ID 的 `secid`。
2. 用东方财富搜索接口确认代码与市场编号：
   ```bash
   curl "https://searchapi.eastmoney.com/api/suggest/get?input=NVDA&type=14&token=D43BF722C8E33BDC906FB84D85E326E8&count=5"
   ```
3. 在 `symbols.json` 中手工写入 `secid`，注明 `method: "seed"` 与 `checked` 日期。
4. 重新 fetch，核对名称、价格、币种与市值量级。
5. 若确实没有可靠来源：设置 `quote_venue = "unpriced"`；页面会说明原因，并把该公司排除在统计之外。

### 6.3 汇率失败

**症状**：`fx.status = stale/fallback`，跨币种市值看起来不对。

1. 检查 `open.er-api.com` 是否可达。
2. 系统会自动回退到东方财富外汇对，再回退到上一份快照。
3. 若故障持续：更新 `sources/fx.py` 中的 `STATIC_FALLBACK`（记录日期），并在 Issue 中说明。
4. 绝不要手工写入未经核实的汇率。

### 6.4 新闻抓取失败

**症状**：首页“行业动态”为空或仍为旧数据。

- 新闻是**非关键路径**：构建不得因此失败。
- 检查 feed URL 是否变化；更新 `config.RSS_FEEDS`。
- 若某家媒体长期不可用，从白名单移除并记录原因。

### 6.5 构建失败

1. 查看 Actions 日志，定位步骤：`refresh` / `validate` / `deploy`。
2. 本地复现：
   ```bash
   python -m semcore build
   python -m semcore validate
   python -m pytest
   ```
3. 若问题在数据：修复 `universe.csv`、`taxonomy.json` 或内容 front matter。
4. 若问题在模板：本地运行 `serve` 检查页面，并补充构建测试。
5. 用 `git revert` 回滚最近一次提交，然后重新触发部署。

### 6.6 页面结构或样式回归

1. 明确影响范围：单页 / 单语言 / 全站。
2. 本地构建并对比截图。
3. 修复后运行全量测试与 `validate`。
4. 若问题来自第三方字体或浏览器兼容：优先使用系统字体栈，不引入 CDN。

### 6.7 读者反馈的数据错误

1. 要求提供来源（公告或交易所页面）。
2. 判断是**来源错误**还是**映射错误**：
   - 来源错误：在 Issue 中记录，等待上游修正；不要手工覆盖。
   - 映射错误：修复 `symbols.json` 或 `universe.csv`。
3. 在 `CHANGELOG.md` 记录修复，并在 Issue 中回复。

### 6.8 安全事件

- 仓库没有密钥、数据库或用户数据；主要风险是依赖漏洞与恶意 PR。
- 启用 Dependabot；审阅外部 PR 中对 workflow 的改动。
- 不要在 Actions 中用 `pull_request_target` 执行不可信代码。
- 若发现恶意内容：立即回滚，轮换 GitHub Token，并审查最近的部署。

## 7. 变更管理

### 7.1 变更类型

| 类型 | 影响 | 要求 |
| --- | --- | --- |
| 数据修正 | 一家公司 / 一条术语 | 附来源；更新快照或主数据 |
| 内容新增 | 知识长文 / 术语表 | 四种语言齐全；CI 通过 |
| 样式 / 模板 | 全站视觉 | 截图对比；检查移动端与深色模式 |
| 方法变更 | 分数、清单、市场状态 | 更新 METHODOLOGY + 站内页 + CHANGELOG + 主版本号 |
| 依赖升级 | 构建环境 | 锁定版本；运行全量测试 |

### 7.2 版本号

- **主版本**：信息架构、评分方法或数据契约的向后不兼容变更。
- **次版本**：新增页面、语言、数据源或覆盖扩展。
- **补丁**：数据修正、文案与样式修复。

### 7.3 发布流程

1. PR → CI（`quality.yml`：测试 + 数据校验 + 构建）。
2. 审核：数据变更需要来源；方法变更需要影响说明；内容变更需要四种语言齐全。
3. 合并到 `main` → `pages.yml` 构建并部署。
4. 更新 `CHANGELOG.md` 与版本号（如适用）。
5. 部署后抽查：首页、一个公司页、一个知识页，以及每种语言版本各一个页面。

## 8. 治理

### 8.1 样本准入

新增公司必须：

- 已上市且可交易；
- 收入主要来自半导体（或明确标注为相邻环节）；
- 有可靠的行情来源；
- 填补环节或地区空缺，或是关键龙头。

移除条件：退市、被收购、业务转型，或连续六个月没有可靠数据。

### 8.2 分类争议

- 以最近一个财年的主要收入来源为准；
- 在 PR 中提供证据（年报中的分部收入）；
- 确实难以判断时，保留在“模组/系统”或“设计”环节，并在公司备注中说明。

### 8.3 方法治理

- 任何权重调整都需要离线对比（分数分布、清单变化）。
- 阈值调整需要说明动机与影响。
- 绝不为了让某家公司进入清单而修改方法。

### 8.4 内容治理

- 原创解释并附引用来源；不要完整复制受版权保护的文本。
- 四种语言版本承载同等信息；不要生产“英文完整版 + 缩短译本”。
- 每篇文章记录更新日期与难度等级。

## 9. 成本

| 项目 | 用量 | 成本 |
| --- | --- | --- |
| GitHub Actions | 每日 1 次 × 约 5 分钟 + PR | 公开仓库免费额度内 |
| GitHub Pages | 静态托管 | 免费 |
| 行情 / 汇率 / RSS | 公开接口 | 免费 |
| 域名 | 默认 `github.io` | 0；自定义域名另计 |

**目标：月度现金成本为零；维护者时间 ≤ 2 小时/月（不含内容创作）。**

## 10. 备份与回滚

- 代码与快照保存在 Git 历史中，天然就是备份。
- 站点可以从任意提交重建：`git checkout <sha> && python -m semcore build`。
- 部署回滚：回滚提交并重新运行 `pages.yml`。
- 保留最近 30 份快照；更早的数据可以从 Git 历史恢复。

## 11. 依赖与许可

- 运行时依赖只有 `jinja2` 与 `requests`；测试使用 `pytest`。
- 依赖升级通过 PR 进行，并锁定主版本范围。
- 数据与新闻版权归提供方；本站不转售、不批量再分发。
- 代码为 MIT；文字内容为 CC BY 4.0。

## 12. 退役预案

若项目停止维护：

1. 在 README 与首页标注“已停止更新”，并说明最后的数据日期。
2. 保留仓库与 `docs/` 为只读，不删除历史。
3. 导出 `data/snapshots/latest.json` 与 `latest_data.json`，并说明字段定义。
4. 移除 Actions 定时任务，停止继续请求上游。
